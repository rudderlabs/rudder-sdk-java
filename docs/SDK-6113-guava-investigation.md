# SDK-6113: Guava deserialization advisory (alert #3)

**Status (2026-11-06): investigation only; no remediation selected or release authorized.** Copy this evidence into [SDK-6113](https://linear.app/rudderstack/issue/SDK-6113) before preparing a remediation PR. This environment has no Linear credentials, so it cannot update the ticket. Do not approve either existing Guava PR as a fix for this alert.

## Dependency and exposure

- [`pom.xml`](../pom.xml) manages `com.google.guava:guava` at **32.1.2-jre**; [`analytics-core/pom.xml`](../analytics-core/pom.xml) directly declares it with **provided** scope and inherits that version. [`analytics/pom.xml`](../analytics/pom.xml) depends on core; [`analytics-sample/pom.xml`](../analytics-sample/pom.xml) depends on analytics. These are source-POM facts, not an effective Maven tree or consumer-facing flattened POM. GitHub's initial alert reports a *runtime*, direct dependency on core; confirm the discrepancy in the [authenticated alert #3](https://github.com/rudderlabs/rudder-sdk-java/security/dependabot/3). Unauthenticated alert API access returned 401; its present state and dependency evidence remain unknown.
- [GHSA-xxph-c9ww-hj94 / CVE-2026-102554](https://github.com/advisories/GHSA-xxph-c9ww-hj94) affects Guava >= 4.0 through 33.7.1 and names uncontrolled allocation while deserializing `CompactHashMap`, `CompactHashSet`, or `MapMakerInternalMap`; 33.7.2 is listed as patched. The SDK's [`messages/ImmutableMap.java`](../analytics-core/src/main/java/com/rudderstack/sdk/java/analytics/messages/ImmutableMap.java) checks for Guava and calls `com.google.common.collect.ImmutableMap.copyOf` when present, otherwise copies into an unmodifiable JDK `LinkedHashMap`. Message builders use this helper to snapshot maps. A search of repository Java sources found neither `ObjectInputStream` nor direct calls to the named classes. The SDK has no identified deserialization entry point for these classes; this does **not** prove that a consumer cannot deserialize a vulnerable Guava object supplied on its own runtime classpath. Do not equate the `copyOf` path with the advisory trigger.
- Existing [PR #155](https://github.com/rudderlabs/rudder-sdk-java/pull/155) and [PR #180](https://github.com/rudderlabs/rudder-sdk-java/pull/180) were open and unmerged at inspection. Both propose **33.7.1-jre**, still inside the advisory range. Coordinate with their owners; update or supersede rather than duplicate them. Recheck PR state before work resumes.

## Candidate and consumer impact (not yet validated)

[Guava v33.7.2](https://github.com/google/guava/releases/tag/v33.7.2) identifies `com.google.guava:guava:33.7.2-jre` as the patched JRE artifact; [its README](https://github.com/google/guava/blob/v33.7.2/README.md) describes JRE support as Java 8+. Repository [`pom.xml`](../pom.xml) targets Java 8 bytecode, but [CI](../.github/workflows/build-and-quality-checks.yml) builds with JDK 17. Upstream [32.1.2](https://github.com/google/guava/blob/v32.1.2/guava/pom.xml) and [33.7.2](https://github.com/google/guava/blob/v33.7.2/guava/pom.xml) POMs differ in transitive declarations (notably `failureaccess` 1.0.1 -> 1.0.3, added `jspecify` 1.0.1, removed Guava's `jsr305` and `checker-qual`; updated `error_prone_annotations` and `j2objc-annotations`). Core separately declares `jsr305`. These upstream POM comparisons do not establish this reactor's effective graph. Direct requests to Maven Central returned 403 and Maven/JDK are unavailable here: artifact resolution, effective transitives, Java 8 runtime compatibility and caller behavior have **not** been tested.

A conditional remediation candidate is **only** changing `<guava.version>` in the parent POM to `33.7.2-jre`, *if* resolution and compatibility checks pass. No host-code change has been identified from the caller; preserve `provided` scope and conditional map-copy behavior. A provided dependency is not guaranteed to bring a patched Guava into downstream runtimes: applications that supply their own Guava must check/upgrade that version independently. Do not change scope or remove the fallback merely to clear the alert. If the candidate cannot be resolved or validated, retain this investigation-only status and assess a mitigation instead.

| Package | Expected effect if version-only candidate is validated | Consumer classification now |
| --- | --- | --- |
| `analytics-parent` | Managed Guava version changes; published parent POM and inheriting builds may resolve a newer provided dependency. | **Unknown** until flattened parent POM and inheritance/resolution are checked. |
| `analytics-core` | Compile/test Guava changes; provided dependency should remain provided in its published POM, so it must not automatically supply a consumer runtime. Map snapshots and null handling need verification. | **Unknown** pending Java 8/17, caller and published-POM checks. |
| `analytics` | Depends on core; no direct Guava declaration; downstream transitive/runtime resolution must be measured. | **Unknown** pending runtime-filtered dependency tree and consumer test. |
| `analytics-sample` | Depends on analytics and packages a jar-with-dependencies; inspect both runtime tree and assembly contents. | **Unknown** pending build and artifact inspection. |

No migration is identified for a version-only, provided-scope change, but consumers using vulnerable Guava at runtime will need to upgrade independently. A regression in behavior, supported runtimes, or a changed scope would require a separate compatibility and migration assessment before release. No SDK release is due for this investigation-only memo. If a compatible remediation is merged, follow [Release Please policy](../release-please-config.json) (one root Java package) and [release process](RELEASING.md) to determine/version the SDK release; use a conventional `fix(deps): ...` PR title and ensure the intended merge commit triggers the expected release. A confirmed break needs `!` in the merged conventional-commit header or a `BREAKING CHANGE:` footer, not merely a PR description. Do not merge or publish on this memo alone.

2. Resolve `com.google.guava:guava:33.7.2-jre` from configured repositories. Compare effective transitive dependency graphs with baseline, then make the **version-only** change if viable. Verify the Java 8 consumer runtime and JDK 17 build; run map-copy/message-builder tests with Guava present and absent at consumer runtime (including snapshots and existing null-key/value behavior). Assert the core's provided contract in the flattened POM, and inspect parent/core/analytics/sample POMs plus the sample assembly and published artifacts for consumer effects. Do not mistake Java 8 source/target or unit tests run only with Guava for a Java 8/no-Guava consumer test.

The POM script checks versions and metadata, **not** Guava scope. Record concrete results for each package and any required host changes in SDK-6113 before requesting review.
4. For a merged fix, follow [RELEASING.md](RELEASING.md): check Release Please candidate and required checks, signed Central artifacts, clean-cache public resolution and exact published-package E2E; then check the **fresh native alert** state and record SDK and consumer upgrade obligations in SDK-6113.
